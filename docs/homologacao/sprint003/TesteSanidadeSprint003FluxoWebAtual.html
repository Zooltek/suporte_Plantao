Teste de Sanidade Sprint 003 - Fluxo Web Atual

Documento manual para homologação do fluxo web atual do sistema. Este roteiro preserva os mesmos 7 cenários do PDF antigo, mas foi reescrito com base na interface e no comportamento reais da aplicação.

Objetivo

Permitir que o usuário execute a sanidade de ponta a ponta sem depender de API, banco ou conhecimento técnico interno.

O foco é confirmar se o fluxo pode ser concluído pela interface, com clareza, feedback e acessibilidade mínimas.

Perfis necessários

  • 1 usuário agente/staff ativo
  • 1 usuário administrador ativo
  • 1 cliente com módulos contratados cadastrados
  • 1 navegador atualizado com captura de tela disponível

Dados para preencher antes da execução

  • Usuário agente/staff: __________________________________________
  • Usuário administrador: _________________________________________
  • Cliente com módulos contratados: ________________________________
  • Arquivo de teste para anexo em tarefa: __________________________
  • Data/hora da execução: _________________________________________

Como executar corretamente

  • Use apenas a interface web. Não use URL escondida, API, console do navegador ou banco.
  • Se uma ação não estiver visível na tela, trate isso como falha de fluxo, não como erro do testador.
  • Em cada cenário, tente pelo menos uma navegação usando teclado: Tab, Shift+Tab, Enter e Espaço.
  • Sempre registre evidência quando houver erro, mensagem ambígua, botão ausente, redirecionamento inesperado ou inconsistência de nome.

Critério de severidade

  • Bloqueador: o usuário não consegue continuar o fluxo.
  • Alto: o fluxo termina, mas com risco real de operação incorreta ou retrabalho.
  • Médio: confusão de nomenclatura, feedback insuficiente, baixa clareza ou problema de acessibilidade contornável.
  • Baixo: detalhe visual, texto pouco claro ou melhoria recomendada sem impacto direto na execução.

Índice dos 7 cenários

  1. Login do usuário staff
  2. Abertura de ticket e validação de status/módulos
  3. Listagem de chamados e filtro por agente
  4. Agendamento e registro de RAT
  5. Criação de tarefa com anexo
  6. Mudança de status de tarefa e notificação
  7. Fluxo de implantação

Observação importante: hoje existe uma inconsistência de nomenclatura entre algumas telas, como "Novo Ticket" no menu lateral e "Novo Chamado" em CTA interno. Se ambos levarem ao mesmo formulário, registre como inconsistência de nomenclatura, mas não bloqueie a execução.

1. Login do usuário staff

Perfil: Agente/Staff Prioridade: Alta Entrada: /admin/login

Objetivo

Confirmar que um usuário staff ativo consegue entrar pela rota canônica e acessar o painel sem erro de sessão.

Passos

  1. Acesse a página de login administrativo.
  2. Valide se a tela mostra o título "Acesso Restrito", os campos "Usuário" e "Senha" e o botão "Acessar Conta".
  3. Preencha as credenciais do usuário staff ativo.
  4. Envie o formulário.
  5. Se possível, faça logout e repita com senha inválida para validar a mensagem de erro.

Resultado esperado

  • O login válido redireciona para o painel do agente/staff.
  • O login inválido exibe feedback claro sem quebrar a tela.
  • Não há loop de redirecionamento, tela em branco ou mensagem técnica.

Usabilidade e acessibilidade

  • A ordem do teclado deve ser lógica: usuário, senha, manter conectado, botão.
  • Os campos devem ter rótulo visível e clicável.
  • Mensagens de erro devem ser legíveis, próximas do formulário e em linguagem humana.
  • O foco do teclado deve ficar visível durante toda a navegação.

Evidência sugerida

  • Print da tela antes do login.
  • Print da área logada após o login.
  • Print da mensagem de erro no teste com senha inválida, se executado.

2. Abertura de ticket e validação de status/módulos

Perfil: Agente/Staff Prioridade: Alta Menu: Atendimento > Novo Ticket

Objetivo

Garantir que o formulário de ticket atual permite abrir chamados, exibe módulos contratados por cliente e direciona corretamente o fluxo de visita técnica.

Passos

  1. Acesse Atendimento > Novo Ticket.
  2. Confirme a presença dos campos principais: Técnico/Suporte, Empresa/Cliente, categoria, subcategoria, Módulo Contratado e Observação Interna.
  3. Selecione um cliente que tenha módulos contratados e verifique se o campo Módulo Contratado exibe opções coerentes com esse cliente.
  4. Abra um ticket sem técnico atribuído e conclua o salvamento.
  5. Abra um novo ticket com técnico atribuído e status operacional equivalente a Em andamento.
  6. Abra um terceiro ticket com status Visita Técnica.

Resultado esperado

  • O formulário carrega sem erro técnico e com os campos visíveis.
  • Os módulos mudam conforme o cliente selecionado.
  • Quando não há técnico, o chamado deve seguir como pendente.
  • Quando o status é Visita Técnica, o sistema deve redirecionar para a criação de agendamento.
  • Status comuns, como Em andamento, não devem redirecionar para agendamento.
Como julgar a etapa: se "Novo Ticket" e "Novo Chamado" aparecerem em pontos diferentes da navegação, mas abrirem o mesmo formulário, classifique como inconsistência de nomenclatura (médio), não como bloqueador.

Usabilidade e acessibilidade

  • O usuário deve conseguir entender claramente qual cliente está selecionado.
  • O estado "cliente bloqueado financeiramente" deve ser visível por texto, não apenas por cor.
  • Campos obrigatórios devem ser fáceis de identificar.
  • O redirecionamento para agendamento, quando houver visita técnica, deve deixar claro o motivo da mudança de tela.

Evidência sugerida

  • Print do formulário com módulos contratados carregados.
  • Print do ticket salvo sem técnico.
  • Print do redirecionamento para agendamento no caso de Visita Técnica.

3. Listagem de chamados e filtro por agente

Perfis: Agente e Admin Prioridade: Alta Menu: Atendimento > Meus Chamados / Todos os Chamados

Objetivo

Verificar se a listagem se comporta corretamente para cada perfil e se o filtro por agente funciona apenas quando o perfil permite.

Passos

  1. Logado como agente, acesse Atendimento > Meus Chamados.
  2. Confirme se a tela mostra o título "Meus Chamados" e a indicação de que o responsável está fixo no usuário logado.
  3. Faça logout e entre com o usuário administrador.
  4. Acesse Atendimento > Todos os Chamados.
  5. Use o filtro Agente para selecionar um responsável específico.
  6. Aplique o filtro e valide se a lista retornada faz sentido para o agente escolhido.

Resultado esperado

  • O agente vê a visão Meus Chamados como padrão.
  • O administrador consegue acessar Todos os Chamados.
  • O filtro por agente deve existir para admin e não deve induzir o agente comum a procurar algo que ele não pode usar.
  • A lista deve atualizar sem erro e sem misturar resultados de outros agentes quando o filtro estiver aplicado.

Usabilidade e acessibilidade

  • Os filtros devem ter nomes claros: palavra-chave, status, categoria, empresa, agente.
  • O botão de aplicar filtro deve ser fácil de identificar.
  • O usuário deve conseguir limpar o filtro sem precisar editar a URL manualmente.
  • O título da página deve deixar evidente se a visão é pessoal ou administrativa.

Evidência sugerida

  • Print de Meus Chamados no perfil agente.
  • Print de Todos os Chamados com filtro por agente no perfil admin.

4. Agendamento e registro de RAT

Perfis: Agente e Admin Prioridade: Alta Entrada: redirecionamento de Visita Técnica ou Novo Agendamento

Objetivo

Confirmar o fluxo atual de agendamento, a confirmação administrativa e o registro de RAT pela interface.

Passos

  1. Partindo do cenário 2, use um ticket com status Visita Técnica para chegar na tela de Novo Agendamento.
  2. Confirme se o contexto do ticket aparece na tela: número do ticket, cliente, contato e título sugerido.
  3. Salve o agendamento.
  4. Entre com o perfil administrador e localize o agendamento na visão de agenda onde ele aparece com o selo "Aguardando admin".
  5. Clique em Confirmar.
  6. Volte ao perfil agente e abra o detalhe do agendamento.
  7. Clique em Novo RAT, preencha data, horário, módulo, executor e contato, e salve.

Resultado esperado

  • O agendamento de origem em ticket mostra o contexto correto.
  • O admin consegue identificar visualmente que o agendamento depende de confirmação.
  • Depois do RAT, o sistema deve redirecionar para o detalhe do agendamento com mensagem de sucesso.
  • O RAT criado deve ficar visível na área de registros do agendamento.

Usabilidade e acessibilidade

  • A tela deve explicar por texto que o agendamento está aguardando confirmação do administrador.
  • O botão Novo RAT deve ser fácil de localizar no detalhe do agendamento.
  • O formulário de RAT deve usar labels claros e separação visual entre contexto e campos editáveis.
  • O retorno após salvar deve mostrar feedback explícito, não apenas mudar a URL.

Evidência sugerida

  • Print do contexto do ticket na tela de agendamento.
  • Print do selo Aguardando admin e do botão Confirmar.
  • Print do detalhe do agendamento após salvar o RAT, com a mensagem de sucesso.

5. Criação de tarefa com anexo

Perfil: Agente ou Admin Prioridade: Alta Menu: Tarefas > Minhas Tarefas

Objetivo

Validar a inbox compartilhada de tarefas, a abertura do drawer e o envio de anexo pelo fluxo web atual.

Passos

  1. Acesse Tarefas > Minhas Tarefas.
  2. Confirme se a tela mostra Minhas Tarefas, o botão Nova Tarefa e o sino de Notificações.
  3. Abra o drawer de criação.
  4. Preencha título, descrição e responsável.
  5. Se necessário, selecione cliente, projeto, módulo e submódulo.
  6. Anexe um arquivo válido de teste com tamanho inferior a 50 MB.
  7. Salve a tarefa.
  8. Opcional: repita com um arquivo acima de 50 MB para validar a mensagem de erro.

Resultado esperado

  • O drawer abre e fecha sem quebrar a navegação.
  • O nome do arquivo selecionado aparece antes do envio.
  • Após salvar, a tarefa é criada sem erro técnico.
  • No teste opcional, um arquivo acima de 50 MB deve exibir erro de validação compreensível.

Usabilidade e acessibilidade

  • O drawer deve manter foco navegável por teclado.
  • O campo de anexo deve informar tipos aceitos e limite de tamanho em texto.
  • Mensagens de erro de validação devem ficar visíveis sem exigir rolagem excessiva.
  • O formulário não deve depender apenas de placeholder para explicar o campo.

Evidência sugerida

  • Print da inbox com o botão Nova Tarefa.
  • Print do drawer com o arquivo selecionado.
  • Print da mensagem de sucesso ou do erro de validação acima de 50 MB.

6. Mudança de status de tarefa e notificação

Perfil: Agente ou Admin Prioridade: Bloqueador se ausente Menu: Tarefas > Minhas Tarefas

Objetivo

Verificar se o usuário consegue alterar o status de uma tarefa diretamente pela interface web e se há retorno visível dessa ação.

Passos

  1. Acesse uma tarefa já criada na inbox.
  2. Procure uma ação visível para alterar status, como botão, dropdown, modal, detalhe expandido ou tela própria de edição.
  3. Se a ação existir, altere o status e valide o retorno visual.
  4. Se a ação não existir, registre o bloqueio e não tente contornar por rota manual, API ou banco.
Resultado esperado no estado atual: se não houver controle visível para mudança de status na UI web, registrar Bloqueador. A ausência dessa ação deve ser tratada como falha do fluxo, não como falha de execução do teste.

Resultado esperado

  • O usuário deveria conseguir localizar uma ação clara para mudar o status.
  • Após a mudança, a interface deveria mostrar feedback de atualização e refletir o novo estado.
  • Se essa ação não existir, o cenário deve ser encerrado como bloqueado.

Usabilidade e acessibilidade

  • A ação de status precisa ser visível sem depender de conhecimento interno do sistema.
  • O status atual deve ser legível em texto, não apenas por cor.
  • Se houver notificação, ela deve ser compreensível e não desaparecer rápido demais para leitura.

Evidência sugerida

  • Print da inbox mostrando a tarefa.
  • Print da ausência da ação de mudança de status, se aplicável.
  • Se a ação existir, print do antes e depois da alteração.

7. Fluxo de implantação

Perfis: Agente e Admin Prioridade: Alta Menu: Implantação > Visão Geral / Agendamentos

Objetivo

Confirmar que o fluxo de implantação atual permite navegar pela área, visualizar agendamentos, registrar RAT e identificar claramente a etapa de finalização.

Passos

  1. Logado como agente, acesse Implantação > Visão Geral.
  2. Confirme a presença dos atalhos Ver Agendamentos e Novo Agendamento.
  3. Acesse Implantação > Agendamentos e confirme se a lista mostra os agendamentos ativos.
  4. Com um agendamento pendente de confirmação, entre com o perfil admin e localize a etapa de confirmação na agenda de agendamentos.
  5. Confirme o agendamento.
  6. Volte ao perfil agente, abra o detalhe do agendamento e registre um RAT.
  7. Tente localizar uma ação visível para finalizar o agendamento pela interface.
Resultado esperado no estado atual: se não houver botão ou ação visível de finalização no fluxo web, registrar Bloqueador. O usuário não deve ser instruído a adivinhar rotas ou usar mecanismos internos.

Resultado esperado

  • A área de implantação deve ser compreensível para o agente: visão geral, listagem e detalhe.
  • O admin deve conseguir identificar e confirmar o agendamento pendente.
  • O detalhe do agendamento deve exibir a seção de RATs e permitir novo registro.
  • A finalização, se não estiver disponível na UI, deve ser registrada como falha de fluxo.

Usabilidade e acessibilidade

  • Os atalhos da área de implantação devem ter nomes claros e consistentes.
  • O selo Aguardando admin deve ser textual e fácil de localizar.
  • O detalhe do agendamento deve separar visualmente dados do agendamento e registros de RAT.
  • Se a tela não oferece ação de finalizar, isso precisa ser tratado como lacuna real de usabilidade do fluxo.

Evidência sugerida

  • Print da Visão Geral da implantação.
  • Print da lista de agendamentos.
  • Print do detalhe do agendamento com a seção de RAT.
  • Print mostrando a ausência de ação de finalizar, se aplicável.
